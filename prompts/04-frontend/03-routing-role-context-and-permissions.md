# تنفيذ المرحلة 03: التوجيه وسياق المستخدم والصلاحيات التجريبية

## الهدف
بناء طبقة التنقل وسياق المستخدم والأدوار والصلاحيات على مستوى الواجهة، بطريقة بسيطة ومركزية وقابلة للاستخدام في جميع الصفحات.

## نطاق التنفيذ
### 1. Routing
أنشئ مسارات واضحة وقابلة للتوسع، على الأقل:

```text
/
/tasks
/deposits
/deposits/:depositId
/investment-requests
/investment-requests/new
/investment-requests/:requestId
/investment-requests/:requestId/:section
/reports
/settings
/access-denied
/*
```

مسار `:section` هو رابط مباشر لأقسام مساحة عمل الطلب ويجب تعريفه صراحة (القرار DEC-015).

- استخدم lazy loading للصفحات الكبيرة عند الحاجة.
- أضف صفحة Not Found جميلة ومتوافقة مع الهوية.
- حافظ على active navigation بدقة.
- لا تضف route لا يوجد له غرض موثق.

### 2. Mock users and roles
أنشئ مستخدمين تجريبيين واقعيين للأدوار التالية:
- أخصائي ودائع.
- مدير عام الخزينة.
- المدير التنفيذي لقطاع الاستثمار والخزينة.
- أخصائي دعم الاستثمار.
- أخصائي المالية.
- أخصائي المحاسبة.
- مدير النظام.
- مستخدم للعرض فقط.

استخدم الأسماء والأدوار المعتمدة في `docs/05-data/demo-users.md` دون اختراع أدوار جديدة.

يجب أن يكون تبديل المستخدم من App Shell واضحًا ومناسبًا للعرض التجريبي.

### 3. Central permission model
أنشئ permission model مركزيًا، ولا تضع شروط الأدوار المبعثرة داخل JSX.

أمثلة للقدرات:
- عرض الطلبات.
- إنشاء طلب.
- تعديل المسودة.
- إرسال الطلب.
- اعتماد أو إعادة الطلب.
- إدخال بيانات البنك الفائز.
- مراجعة دعم الاستثمار.
- مراجعة المالية.
- تنفيذ المحاسبة.
- تأكيد التفعيل.
- إدارة الإعدادات.
- عرض التقارير.

الصلاحيات يجب أن تعتمد على الدور، ويمكن لاحقًا دمجها مع حالة المعاملة دون إعادة كتابة التطبيق.

### 4. User context
أنشئ Context أو store خفيفًا يوفر:
- المستخدم الحالي.
- الدور الحالي.
- قائمة الصلاحيات.
- تبديل المستخدم.
- helpers مثل `can()` أو ما يعادلها.

لا تضف Authentication حقيقيًا أو tokens أو Microsoft Entra integration.

### 5. Route-level access
- منع الوصول غير المصرح به بطريقة واضحة.
- إظهار Access Denied state جميلة بدل شاشة فارغة.
- لا تخفِ فقط عناصر القائمة مع إبقاء المسار مفتوحًا دون حماية تجريبية.

## معايير الجودة
- لا تكرر أسماء الأدوار والصلاحيات في عدة ملفات.
- استخدم enums أو union types دقيقة.
- لا تستخدم strings سحرية مبعثرة.
- تبديل المستخدم ينعكس فورًا على القائمة والمحتوى المتاح.
- لا تضف business workflow كاملًا في هذه المرحلة.
- واجهة role switcher لا تشوّه App Shell ولا تبدو أداة مطور رخيصة.

## معايير القبول
- جميع المسارات تعمل.
- Not Found وAccess Denied موجودتان.
- الصلاحيات مركزية وقابلة للاختبار.
- role switching يعمل دون refresh.
- RTL وresponsive سليم.
- ينجح typecheck وlint وbuild.

## تقرير الإنجاز
اذكر المسارات، الأدوار، بنية الصلاحيات، وأي افتراض تم تجنبه لعدم وجود متطلب موثق.
